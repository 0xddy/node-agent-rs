## 值得采纳的意见

- **正常 FTPS 矩阵的覆盖边界应说得更明确。** `ftp.go` 在 graceful 模式先发送 TLS
  关闭通知、读取反向至 EOF，然后才关闭底层流。这避开了本次“反向未结束时取消接收”
  的关闭时序。因此 FTPS 矩阵通过能证明这些正常传输的完整性，不能验证故障触发路径；
  缺陷的前后差异仍来自独立 Rust 回归。下一轮应增加受控关闭时序的真实 FTPS 对照。
- **直连 FTPS 截断应作为竞争假设保留。** 它不能证明 node-agent 有问题，也不能证明
  FileZilla 实际采用相同关闭方式；但“没有代理也可能出现短文件和 226”值得在现场排查中
  明示。此前报告没有认定它与现场无关，章节安排仍可加强这一点。
- **持续排空存在资源消耗边界。** 已认证且路由允许的客户端，可触发 `peer_stopped`，
  让目标持续发送、代理持续读取并丢弃。该部分绕过用户下载计量和限速，总流量及持续
  时间没有单独上限。缓冲、每连接流数、协作调度及整个连接的生命周期取消仍然有效，
  所以应描述为目标侧网络与 CPU 的持续消耗，不是无限内存缓存，也不是免费向客户端
  传送下载内容。上传结束后的独立排空预算值得设计和回归验证。
- **release 诊断和 vendored 来源需要明确。** `shoes-plus/Cargo.toml:63` 确有
  `release_max_level_info`，HY2 复制失败的 debug 日志不适合现场留证。流控耗尽时仍先报告
  Stopped 的改动来源，已核对为相邻 `shoes-plus` 的提交
  `fd758ead3fd63d0a732163ff50d30949996c6c68`，不能泛称上游 Quinn 原有行为。

## 不能原样视为已证实事实的表述

- **“所有取消都会给目标干净 FIN”过宽。** 复制器实际返回 Err 后，确会继续调用目标
  `shutdown()`；但 `scope_connection_until_cancelled` 在取消分支直接丢弃整个处理 future，
  不经过该收尾。物理 QUIC 退出和用户生命周期取消有此兜底，普通配置更新也不必然
  终止旧流。此外，后续 socket drop 若还有未读目标数据，仍可能产生 RST。
  应收窄为“某些复制错误路径仍尝试正常关闭目标，可能让失败上传表现为 EOF”，并分别复现。
- **“上传 Done 后加任何超时都不可能再截断”还需证明。** 本地写入与发送 FIN 不等于
  目标应用已经完整读取或落盘。排空预算的关闭方式仍需验证，尤其不能重新引入未读 TCP
  数据和重置导致的尾部丢失；本轮没有实现或测试该方案。
- **连接数、RSS 和累计计量快照需要定位，不等于已证明泄漏或计费错误。** 最终仍有一条
  遥测活动连接、RSS 增长和累计流量差异已在证据中保留。统计刷新时机、连接含义及
  allocator 行为等尚未分别控制，不能只凭一张快照归因到新包装器。
- **受控 FTPS 复现仍不能直接坐实用户现场。** 即使新客户端在旧版失败、新版通过，也只
  能补强该机制；仍需核对用户实际 FileZilla 版本、代理客户端和关闭时序。
- Claude 回复把 118 次称为全部 FTPS 的地方需校正：实际是 118 次 FTP/FTPS 合计，
  其中 2 次明文 FTP、116 次 FTPS，FTPS 中另含 3 次直连对照。

## 下一轮优先顺序

1. 实测明确版本的 FileZilla 与实际 HY2 客户端，记录可核对的关闭事件；保留源/目标
   字节数与 SHA-256，而不仅是界面显示的大小或完成状态。
2. 增加受控提前取消接收的真实 FTPS 修复前后对照，同时保持直连基线可解释；核对
   上传字节、目标文件、服务端 FTP 完成码，避免再次把客户端自身截断当作代理缺陷。
3. 独立验证上传 RESET、物理连接取消及目标异常的收尾行为，再决定是否引入按方向的
   正常关闭/异常关闭策略。
4. 为上传完成后的持续排空设计有界收尾，验证慢目标数据完整性、任务/许可释放和
   遥测最终收敛；增加 release 可见且限频的方向、字节数、关闭状态与错误诊断。

目前结论保持不变：核心半关闭截断缺陷已经证实并修复；用户那次 FileZilla 故障的
实际原因尚未确认。Claude 的审查增加了后续验证方向，没有替代现场证据。

### Linux FileZilla 后续实测

已用 Debian FileZilla 3.63.0、显式 FTPS 和受限 SOCKS5→`sing-quic` HY2 适配器运行
独立 Docker 矩阵。2 次直连对照及 28 次 HY2 上传全部成功；后者包含单路、四路并发、
四个约 32 MiB TS 并发和服务端每连接 2 MiB/s 限读。服务端 30 次 SHA-256 全匹配，
无 incomplete，FileZilla 也记录 30 次成功；HY2 数据流无错误。详细证据见
[完整性报告](hysteria2-ftps-ts-integrity.md#linux-filezilla-真实客户端复验)。

这一结果完成了“明确版本的真实 FileZilla 本地对照”，尚未完成“用户实际 Windows
FileZilla 和实际 HY2 客户端”的现场核对，也没有替代受控提前取消的故障分支回归。

### 快照问题的进一步核对

三轮完成快照中，baseline-final 与 fixed-final 的 active/online 均为 0/0，
final-reviewed 为 1/1。这是 fixture 最近收到的遥测值（`hy2_container_fixture.rs:347`），
不是对实时逻辑任务的检查。运行时按用户的连接上下文求和（`runtime.rs:2286`）；
HY2 每条物理 QUIC 连接建立一个计量上下文，各逻辑流共享（`hysteria2_server.rs:153`）。
因此不能将数字 1 直接解释为“有一个新 drain 逻辑任务泄漏”。

`run.py:239` 在最后传输后立即取快照，没有等待静默收敛。遥测按约 3 秒节拍采样，
流量按 10 秒周期上报增量；fixture 每秒写出最近收到的数据，未保存对应遥测样本原始时间。
三轮 Alice 已收到报告数为 9/9/8，最后几批尚未上报是累计计量差异的可行解释，尚未证实。

三轮 RSS 增量分别为 13,844 / 10,408 / 20,120 KiB。单次前后差不能证明内存泄漏，也
不能要求 allocator 在短时间内把 RSS 完全还原。应新增至少两个流量上报周期的静默
收敛观察，并记录样本时间、物理 QUIC 关闭事件、逻辑任务/许可数，再做归因。

新的 FileZilla runner 已按这个结论执行：完成传输后等待 22 秒，物理 HY2 客户端仍
保持时 active/online 为 1/1；适配器记录 `stopping`、完成 QUIC 关闭并记录 `stopped`
后，遥测回到 0/0，FD 从 16 回到起始的 13。由此可确认本轮数字 1 是仍存活的物理
会话，不是上传逻辑流残留。该有界结果不证明所有异常退出路径都能同样及时收敛。
