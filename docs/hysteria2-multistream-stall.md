# HY2 多流下载结束后的停滞排查

2026-09-03。用户反馈 Speedtest 网页端单线程正常，默认多线程在下载结束、切换上传附近失联，进程仍在运行；Google 测速和普通大文件上传可正常完成。排查需要分别确认进程、单条隧道以及其他用户连接的状态，也需要区分逻辑流并发数和 QUIC 连接数。

## 已确认的流状态错误

`shoes-plus/vendor/quinn-proto/src/connection/streams/mod.rs` 的 `write_source` 在连接发送额度为零时先返回 `WriteError::Blocked`，之后才由底层 `Send::write` 检查流是否已停止。下载写任务等待期间收到正常 `STOP_SENDING`，Quinn 会唤醒该写任务，但重试仍得到 `Blocked`。应用无法及时观察停止错误，因而不能进入退出、drop/reset 的清理路径。

HY2 新逻辑流在目标 TCP 连接建立后，要先[写入成功响应，再开始双向转发](https://github.com/0xddy/shoes-plus/blob/b6c98ea44732c61cd6d996fb45f12618bd311c4f/src/hysteria2_server.rs#L2020)。因此旧下载占住服务端发送额度，也会阻止后续上传进入转发阶段，这与本次目标连接已建立但没有新增上传字节的观测相符。

最小修复将已有的 Closed/Stopped 判断提前到连接额度判断之前，保持错误优先级与 `Send::write` 一致。没有增加发送额度，也没有修改拥塞控制或限速参数。reset 可以归还本地 `send_window` 占用；对端拥有的 `MAX_DATA` 额度仍必须等对端授予，不能自行返还。

两项确定性回归分别耗尽本地发送窗口和对端连接额度，同时阻塞下载流与后续请求，然后送入正常停止事件：

- 修改前：两项均失败，实际 `Blocked`，预期 `Stopped(42)`。
- 修改后：写者观察到停止，reset 清理后后续流恢复可写；`MAX_DATA` 用例明确要求合法的对端窗口更新。
- vendored quinn-proto 完整测试：288 项通过。

对照 [sing-box 使用的 quic-go 发送流实现](https://github.com/SagerNet/quic-go/blob/v0.61.0-sing-box-mod.7/send_stream.go)，停止处理会设置错误、清理发送状态、安排 RESET_STREAM 并唤醒写者；写入入口先检查终止错误，再尝试流控额度。本次修复保留 Quinn 原有的应用清理机制，修正其终止错误被等待额度遮蔽的问题。

此外，`crates/shoes-engine/tests/quinn_stopped_writer.rs` 通过真实回环 UDP 和公开 Quinn API 验证阻塞写者收到 STOP 后退出，再在原 QUIC 上完成新请求。客户端合法声明初始连接接收额度为 0，避免停止操作顺带返还已接收数据的额度而掩盖错误：旧代码等待 5 秒超时，修复后完成。该测试隔离错误处理契约，不是对浏览器流控窗口的推测。

这证明了一个与下载取消时机相符的代码缺陷；以下 Docker 取消用例还复现了进程正常、单条隧道失联的症状。现场网页测试仍需要实际客户端复测确认。

## 分开比较流数和 QUIC 连接数

官方 [sing-quic 的 `Client.DialConn`](https://github.com/SagerNet/sing-quic/blob/v0.7.0-beta.4/hysteria2/client.go) 通过 `offer` 复用活跃连接，再打开 QUIC 逻辑流。因此测试客户端增加 `--connections`，每个独立客户端固定使用一条 UDP/QUIC 连接；`--streams` 表示每连接的逻辑流数，所有流准备好后同时开始，每条主连接拒绝自动重连。

## 取消下载后的 Docker 故障复现

继续使用同一个旧版 Linux daemon，测试正常下载 3 秒后调用官方客户端的逻辑流 `Close`，收齐本地下载任务后立即在原 QUIC 上传；不关闭或重新建立该 QUIC。单流取消后上传 240 MiB 正常。15 流每条下载上限 128 MiB，取消后每条上传 16 MiB，合计 240 MiB，计划重复三轮。旧下载 15 + 新上传 15 + Bob 1 = 31，处于目标的 32 任务容量以内。

18:56–18:57 的旧版结果：

- 第 1 轮 15 路下载取消正常，随后上传完成。
- 第 2 轮 15 路下载取消正常，但随后上传 **60 秒超时**，整个阶段最长无应用进展 **59.475 秒**，没有一条上传完成。

## 独立的本地 I/O 错误清理

同时确认 Quinn 驱动遇到致命本地 I/O 错误直接返回时，存活的连接/流句柄可能让等待中的读写和 `closed()` 永久挂起。补丁在返回原错误前唤醒等待者，关闭队列并释放 endpoint 路由，防止遗留句柄稍后重复清理已复用的连接槽位。已存在的关闭原因保持不变。

两项正常回环连接上的一次性假 socket 错误测试在旧代码均超时，修改后通过；另测保留关闭原因与队列资源回收。此项与上述流控错误分别验证。

默认 Linux Tokio adapter 调用 quinn-udp 的 `send`，普通 UDP 发送错误会被过滤记录，并不会直接进入这个致命分支；假 socket 测试不能用来声称现场出现了这种 I/O 错误。完整实现、来源和可达性边界见核心仓库 `vendor/quinn/PATCH.md`。
